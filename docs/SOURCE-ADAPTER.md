# 接入一个新的注入源

这份文档解决一个问题：以后 surf（或其他生产者）要往对话里塞内容时，怎么接进来，以及**不许**接成什么样子。

## 一、源契约

搬运层对生产者的全部要求，只有一个端点：

```
GET {BASE}{INJECT_PATH}
Authorization: Bearer {TOKEN}

200 OK
{
  "block": "要贴进对话的文本，可含换行；空串表示此刻没有内容",
  "sig":   "状态签名，块内容变化时必变；用于节流去重"
}
```

三条硬性要求：

1. **无副作用**。这个端点会被轮询（默认 30 秒缓存一次），拉取本身不能推进状态、不能记账、不能触发动作。状态推进必须由真正的事件驱动。
2. **`sig` 必须单调可判**。同一个 `sig` 就代表同一段内容。块的措辞变了而 `sig` 没变，等于这段内容永远不会被重新贴出去。
3. **空内容返回空串，不要返回 `null`、不要返回占位文字**。搬运层按"空则跳过"处理。

其余一切（怎么算出来的、涉及几个模型、耗时多久）搬运层都不关心，也读不懂。

## 二、搬运层的处理链

chat 请求进来后，固定顺序：

```
1. 先把原始 messages 快照送给所有声明 observe 的源
2. 依次向各源拉块（缓存内直接命中）
3. 按源顺序拼接 block 字符串
4. 合并 sig（各源 sig 连接）
5. 合并后的 sig 与上次贴出去的一致 → 本次不贴
6. 贴进最后一条 user 消息的最前面
7. 转发给 lattice
```

顺序不能动。第 1 步必须早于第 5 步：判定器要读的是用户原话，不是带块之后的文本。如果先注入再送快照，判定器会把自己上次的输出当成新输入，状态就会自激。

## 三、拼接规则

多源共存时，块与块之间**只做字符串连接，插入一个空行**。

- 不插入连接词（"另外"、"此外"、"顺便"）
- 不做语义去重（两个源都说同一件事，就都保留）
- 不调整顺序（顺序 = 配置里的声明顺序）
- 不做长度裁剪

每个源的内容**自带自己的边界标记**（比如 `【潮汐基频 · CADENCE】` 这类头句）。搬运层不生成、不补全、不删除任何标记。这样主模型看到几段内容、分别来自谁，是可数的。

## 四、故障与降级

| 情况 | 行为 |
|---|---|
| 源超时（默认 3s） | 丢掉该源内容，其余照常贴，转发不延迟 |
| 源 5xx / 返回非法 JSON | 同上，进冷却期（默认 15s 内不再重试） |
| 全部源不可达 | 不注入，请求原样转发 |
| 快照推送失败 | 记日志，不重试、不影响响应 |

铁律：**任何情况下都不许自己造一段内容顶上。** 没有内容就没有内容，对话照常进行。

## 五、接 surf 的具体步骤

前置条件：surf 已经有独立的注入端点。当前 surf 只做产物回投（`POST /surf/finding` → cadence），没有"当前该贴什么"的出口，所以还不能接。

准备就绪后：

1. surf 侧加端点，返回 `{ block, sig }`。`sig` 用产物 id 或时间戳，别用正文哈希（正文里带随机措辞会导致每轮都变）。
2. 搬运层加源条目（`.env`）：

   ```
   SURF_ENABLED=true
   SURF_BASE=http://127.0.0.1:18222
   SURF_TOKEN=
   SURF_INJECT_PATH=/pipeline/inject
   ```

3. 代码里三处小改：
   - `fetchBlock()` 从单源拉取改为遍历源列表（并行拉、按声明顺序拼）
   - 签名合并改为 `sigs.join('|')`
   - `/pipeline/health` 输出每个源的状态（cached / degraded）
4. 灰度：先只开 surf 源、`INJECT_THROTTLE_SECONDS` 调小观察拼接效果，确认头和边界正常后再开 cadence。

## 六、反面案例

以下几种"顺手加一点"的改动，都会让这个仓库失去存在意义：

- 在搬运层判断 surf 产物够不够重要 → 重要性是生产者的判断
- 两个源都有内容时只留一个，避免"显得啰嗦" → 取舍是设计决策，不是搬运决策
- surf 不可达时用上一次的旧内容顶上 → 旧内容过期了，贴出去是错的
- 把两个源的块合并成一段更自然的文字 → 改写即判断，且让来源不可追溯
